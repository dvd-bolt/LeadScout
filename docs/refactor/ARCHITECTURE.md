# Архитектура после завершения рефакторинга

LeadScout остаётся одним приложением и одним процессом. Mini App — основной интерфейс;
бот обеспечивает вход, уведомления и остановку. Отдельные сервисы или микросервисы для
этого разделения не нужны.

## Владение зависимостями

`leadscout.runtime.context.build_context()` собирает независимый граф:

- `Storage(Database(path))`: SQLite и репозитории;
- `Coordination`: блокировки аккаунтов/входа и общий лимит браузерных контекстов;
- `SharedBrowserPool`: движки Chromium по нормализованному прокси;
- `AIIntegration`: свой `GeminiService` и собственный ограниченный кэш;
- менеджеры входа, резюме и вакансий с явно переданными БД, пулом и шифрованием;
- `ApplicationClient`, `RuntimeJobDependencies`, `TaskCoordinator` и уведомления;
- пять бизнес-сервисов и `OperationManager`.

`get_default_context()` лениво создаёт один такой граф для стандартного запуска.
`main.py` и `server_app.py` вызывают общий `run_application()` соответственно без API и с API.
FastAPI получает контекст через `app.state.context`, Aiogram — через `dispatcher["app_context"]`,
APScheduler — через аргументы заданий. Сам `create_app(context)` собирает ASGI-приложение;
инициализацией и закрытием владеет runner, а не скрытые побочные эффекты импорта.

Корневые `database`, `worker`, `ai_handler`, `parsers`, `web_api`, `scheduler_app` —
совместимые адаптеры к стандартному контексту. Их старые изменяемые глобальные переменные
не являются интерфейсом внедрения зависимостей: новые тесты используют `build_context(...)`.
Пакетные сервисы, задания и интеграции не импортируют корневые адаптеры и не ищут объекты
через `sys.modules`. Два независимых контекста можно проверять с одинаковыми ID в разных БД.
Несколько процессов с общей рабочей SQLite-базой и отдельными координаторами не поддерживаются.

## Миграция v5 → v6

Перед DDL миграция вычисляет ключи всех аккаунтов той же функцией, которой пользуются
создание и поиск. Коллизии проверяются внутри пользователя. При совпадении непустых
ключей возникает `MigrationConflictError` со списками ID; схема, строки и версия не меняются.
Автоматического объединения и удаления записей нет.

В одной транзакции исправляются также непустые неправильные ключи, пересоздаётся уникальный
индекс и добавляется `pending_questionnaires.revision INTEGER NOT NULL DEFAULT 0`.
Версия становится 6 только вместе с успешным commit. Повторный запуск безопасен.
Новая БД сразу получает v6. Миграции с более старых поддерживаемых схем сохранены.

Рабочую БД перед обновлением нужно консистентно копировать SQLite backup API вместе с
сохранением исходного Fernet-ключа. Спорную копию нельзя автоматически «исправлять» удалением
дубликатов. Остальная разработка и тестирование независимых временных БД продолжаются.

## Версия анкеты и отправка

`GET /api/v1/questionnaires/{id}` и `PATCH` возвращают `revision`.
PATCH проверяет только переданные ответы: ID, тип, вариант, длину и отсутствие повторных ID.
Обязательные пропущенные ответы разрешены в черновике. Письмо и ответы сохраняются одной
транзакцией, повышающей revision. `answers: []` очищает ответы; отсутствие поля сохраняет их.
Ответ PATCH содержит снимок именно этой транзакции. Отдельного чтения после commit нет:
параллельная запись не может незаметно подменить черновик и версию в ответе сохранения.

`POST /api/v1/questionnaires/{id}/confirm` принимает необязательное
`{"expected_revision": N}`. Новый frontend отправляет версию сохранённого черновика.
Сервер проверяет полноту и захватывает через условный SQL UPDATE именно проверенную версию.
Конкурентное редактирование даёт 409 без запуска задания. Запрос без тела поддержан: сервер
сам читает текущую версию, проверяет её и условно захватывает. Повтор уже исполняемой анкеты
возвращает `ALREADY_RUNNING`, а завершённой — 409; второго задания не создаётся.

При отправке поля и кнопки блокируются. Частота GET открытой отправляемой анкеты — 3 секунды,
ожидающей решения — 15 секунд, завершённой — без периодического индивидуального опроса.
При возврате во вкладку данные обновляются. Мутации и завершение фонового задания обновляют
индивидуальный объект, данные прямой ссылки, список, историю и показатели кабинета.
Ошибки и 409 вызывают перечитывание. Потерянный ответ подтверждения не вызывает повторный POST.

## Ошибки ИИ

Ошибка сравнения `AIServiceError` проходит в сервис и становится `FAILED` в журнале операций.
Пользователь получает сообщение и может повторить сравнение вручную. Корректный ответ модели
с `match_score=0` остаётся `SUCCEEDED`; отсутствие совпадений не равно сбою провайдера.

## Lifecycle

Инициализация централизует миграцию и восстановление прерванных операций/анкет.
Завершение запрещает новые задания, останавливает scheduler, завершает API и polling,
отменяет операции, входы и задания, восстанавливает прерванные состояния и закрывает браузеры,
ИИ-клиент, storage dispatcher и bot session. Uvicorn получает время на штатное завершение,
затем зависшее завершение ограничивается отменой.

Повторные вызовы ожидают одну задачу shutdown. Ошибка закрытия одного ресурса не пропускает
следующие; ошибки собираются в группу. Частичный запуск не требует наличия всех ресурсов.
Миграции, получение ресурсов при запуске и их завершение используют общий lifecycle lock.
Если завершение запрошено во время проверки ИИ при запуске, polling и API уже не стартуют.
Login-сессия отдельно пытается закрыть контекст и движок; менеджер закрывает все сессии
и сообщает о собранных ошибках, а повторное закрытие не повторяет освобождение ресурсов.
Регистрация операции, уже ожидающая запись в БД, включается в завершение и не запускает работу
после остановки. Восстановление никогда не повторяет внешнюю отправку автоматически.

## Проверки

Штатный `pytest` включает исходные девять диагностических сценариев в
`tests/test_refactor_regressions.py`, миграции/коллизии/backup, версии анкет, изоляцию контекстов,
lifecycle, компактный router и старые кнопки. `tests/test_questionnaire_e2e.py` выполняет цепочку
собранный React → настоящий API → сервисы → настоящий координатор/задание → SQLite;
подменены только внешние взаимодействия hh.ru.

`scripts/container_smoke.py` проверяет настоящий HTTP runner, статику Mini App, Chromium,
SQLite, успешную отправку, повтор и остановку с заглушками внешних действий.
`sh scripts/verify-container.sh` собирает образ и запускает эту проверку через отдельный Compose
без сети, `.env`, рабочих томов и опубликованных портов. Успех локального запуска smoke-скрипта
не заменяет проверку Docker image build.


## Несколько владельцев

`RuntimeSettings.owner_telegram_ids` задаёт общий список доступа бота и API. При пустом списке
сохраняется совместимость с `owner_telegram_id`. Конфигурация `OWNER_TELEGRAM_IDS` принимает
ID через запятую или пробел и имеет приоритет над старой переменной. Авторизация проверяет
список при входе и при каждом запросе существующей сессии. Доступ к данным по-прежнему
ограничен `user_id`; общего кабинета между владельцами нет.

## Mono UI — 11 сентября 2026

Оболочка остаётся React + HashRouter + TanStack Query, оформление — CSS Modules.
`web/src/styles/tokens.css` задаёт монохромную палитру и safe-area; `styles.css` —
локальный Inter Variable, базовые элементы, фокус и reduced motion. Лицензия шрифта
лежит рядом с WOFF2 в `web/public/fonts`. Цветовая схема всегда светлая.

`app/AppLayout.module.css`, `pages/HomePage.module.css` и модули AutomationControls,
EventRow и SegmentedProgress отделяют композицию от общих UI-элементов.
`shared/ui/UI.module.css` содержит карточки, формы, статусы и списки внутренних экранов.
Прежний `App.module.css` удалён; CSS-импорты переведены на новую структуру.
SVG-иконки определены локально в `shared/ui/Icon.tsx` без стороннего UI-фреймворка.

`GET /api/v1/me` добавляет `active_pending_review_count`: COUNT анкет выбранного аккаунта
текущего владельца в PENDING/FAILED/NEEDS_REVIEW. Лимит списка из 100 записей не влияет
на этот показатель. Старое `pending_review_count` сохранено. Миграций нет.
Время следующего запуска берётся из того же scheduler контекста, что и список аккаунтов.

Главная, бейдж меню и переход к проверке используют новый счётчик.
`/applications?tab=review|history` выбирает вкладку, `apply_id` имеет приоритет.
Компоненты аккаунта пересоздаются по его ID; сообщения и результаты массовых действий
не переносятся между аккаунтами. Кнопки автоматизации ждут завершения POST и обновления
dashboard. Интерфейс не инициирует запуск, подтверждение или повтор отправки автоматически.

Проверки Mono — `tests/test_mono_design.py` и расширенный набор `tests/parallel_ui`.
Существующие сквозные тесты анкет, revision/409 и координатора сохранены.
