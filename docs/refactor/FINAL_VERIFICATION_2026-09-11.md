## Исправления

| Область | Результат |
|---|---|
| R1: логины | Одна нормализация для создания, поиска и миграции. v6 исправляет непустые ошибочные ключи. Коллизия внутри пользователя останавливает миграцию до изменений и сообщает ID. Индекс, ключи, revision и версия обновляются транзакционно. |
| R2: ИИ | Ошибка сравнения становится FAILED с понятным сообщением; вручную повторённый запрос может завершиться успешно. Настоящий результат 0/100 остаётся SUCCEEDED. |
| R3: черновики | Разрешены неполные анкеты; переданные ответы проверяются. Письмо и ответы сохраняются атомарно. Пустой список очищает ответы; отсутствие поля сохраняет их. Подтверждение проверяет обязательные ответы и условно захватывает ту же revision, иначе 409 без запуска. |
| R4: интерфейс | После подтверждения сохраняется актуальное состояние. Отправка блокирует поля и кнопки; индивидуальный опрос — 3 секунды, ожидающая анкета — 15 секунд. Конечный статус прекращает частый опрос. Обновляются связанные данные и кабинет. Ошибки и 409 перечитывают данные без повторного POST. |

Новые ошибки сначала воспроизводились отдельными тестами. Дополнительно исправлены:

- отображение старого текста после конфликта версии;
- доступность редактирования во время отправки;
- регистрация операции, завершавшаяся уже после начала shutdown;
- незакрытый Playwright при ошибке закрытия Chromium и скрытые ошибки browser pool;
- немедленная отмена API вместо штатного завершения Uvicorn;
- использование настроенного URL конкретного контекста в уведомлениях;
- оставшиеся старые кнопки меню, CAPTCHA и аудитов: теперь они открывают Mini App.

## Завершённое разделение кода

Пять бизнес-сервисов находятся в отдельных модулях `accounts`, `resumes`, `automation`,
`questionnaires`, `audits`. Контракты, ошибки, общие проверки и сборка вынесены отдельно;
`facade.py` сохраняет совместимые импорты.

`AppContext` владеет БД, координатором, менеджерами hh.ru, ИИ/кэшем, браузерным пулом,
синхронизацией и операциями. Стандартный API, бот и scheduler используют этот граф.
Корневые адаптеры делегируют тому же контексту; пакетный код не импортирует их и не ищет
объекты через `sys.modules`. Изоляция двух контекстов с одинаковыми ID в разных БД проверена.

Оба режима запуска используют общий runner/lifecycle. Проверены частичный запуск,
восстановление, отмена задач и повторное завершение; ошибка одного ресурса не пропускает
закрытие остальных. Большая реализация старых Telegram-экранов удалена, тесты перенесены
на действующий компактный router с проверками владельца и безопасных переходов.

Подробности и новые контракты: [ARCHITECTURE.md](ARCHITECTURE.md).

## Остаток перед рабочим запуском

1. В окружении с Docker выполнить `sh scripts/verify-container.sh`. Этот отдельный Compose
   собирает образ, запускает offline smoke без сети, рабочих томов, `.env` и опубликованных
   портов, затем удаляет только свой временный проект. Локальная проверка smoke-скрипта
   подтверждает сам сценарий, но не сборку и совместимость контейнерного образа.
2. Перед обновлением рабочей установки сохранить БД через SQLite backup API и исходный
   Fernet-ключ; сначала проверить миграцию копии. При коллизии остановить применение к этой
   базе, разобрать указанные ID вручную, не объединять аккаунты автоматически.
3. Отдельно подтвердить настоящий вход/CAPTCHA/OTP hh.ru, ответы Gemini, доставку Telegram,
   поведение Mini App внутри Telegram, BotFather/HTTPS и реальные отклики. Эти внешние
   действия и развёртывание в данной работе не выполнялись.
