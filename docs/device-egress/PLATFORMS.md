# LeadScout Connect: реализация на четырёх платформах

Дата: 17 сентября 2026. Платформенные APIs сверены с официальной документацией. Предлагаемые пользовательские сценарии и настройки — проект; они требуют проверки на устройствах. Здесь нет утверждения, что App Store или Google Play уже одобрили приложение.

См. [общую схему](README.md), [протокол](PROTOCOL.md) и [интеграцию/тесты](SERVER-IMPLEMENTATION.md).

## 1. Общая оболочка агента

У всех клиентов один protocol v1 и одинаковые основные экраны:

1. Подключение: код/QR, отпечаток ключа, подтверждённый владелец.
2. Статус: устройство, «Подключено / Остановлено / Нет сети / Нужен запуск», обслуживаемый аккаунт, текущая операция без содержания резюме.
3. Сеанс: начало, остановка, оставшийся срок и объём данных.
4. Сеть: Wi-Fi-only или разрешение мобильных/лимитных сетей, учёт RX+TX.
5. Диагностика: версия, последний код ошибки, отправка технического отчёта по действию пользователя.
6. Настройки: автозапуск где применим, уведомления, обновления, отключение устройства.

Агент не дублирует редактор резюме, историю, оплату или анкету. Для этого открывает Mini App. Нельзя считать «агент запущен» равнозначным «браузер может работать»: сначала handshake, разрешённый режим ОС, lease и route probe.

Предлагаемый общий core: Rust с async runtime, зрелой библиотекой WebSocket и TLS. На смартфонах resolver/socket adapter обязан использовать политику сети ОС; на desktop — обычные TCP-сокеты. Минимальный core сначала собирается на всех targets, затем к нему добавляется полный UI.

Список targets первого цикла сборки:

```text
iOS device:    aarch64-apple-ios
iOS simulator: aarch64-apple-ios-sim
macOS:         aarch64-apple-darwin, x86_64-apple-darwin
Android:       aarch64-linux-android, x86_64-linux-android (emulator)
Windows:       x86_64-pc-windows-msvc; ARM64 — отдельный следующий target
```

Это список проектных целей, не проверенные сборки. ARMv7 Android и старые Windows не включаются автоматически. SDK/toolchain/минимальные ОС фиксируются в CI после первой успешной межплатформенной сборки. Нативное приложение не получает shell-команд с сервера и не исполняет загружаемый код.

## 2. iOS / iPhone

### 2.1 Два режима, которые нельзя смешивать

**Базовый режим: агент виден на экране.** Нативное приложение держит control/data соединения и выполняет передачу. После ухода в фон оно готовится к приостановке. Короткое дополнительное время `beginBackgroundTask` используется для остановки и сохранения состояния, а не как обещание полного рабочего сеанса.

**Экспериментальный для iOS 26+: конечная задача, которую пользователь запустил в агенте.** `BGContinuedProcessingTask` позволяет продолжить работу после сворачивания, в том числе сетевую. Предусмотрены прогресс и отмена. Система может завершить задачу; применение API к нашему relay необходимо проверить отдельно. [Apple: длительные задачи](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/).

Это не постоянный socket daemon, не гарантированное расписание и не право серверу открывать новые сеансы без пользователя. Более раннее предположение «любой iPhone может работать как постоянный прокси после установки приложения» не должно попасть в требования или маркетинг.

### 2.2 Почему не VPN extension

Для v1 не использовать `NEPacketTunnelProvider`, фиктивный VPN, аудио, location или VoIP как способ удержать процесс. Apple прямо указывает, что размещение listener/proxy server не относится к рекомендованным сценариям packet tunnel provider. [TN3120](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers).

Наш поток — из серверного браузера через приложение к hh.ru. Он не является обычным туннелированием сетевого трафика самого iPhone. Создание VPN-профиля не делает этот сценарий автоматически поддержанным. MDM/enterprise distribution также не является продуктовой заменой массовой установки для частных пользователей.

### 2.3 Состав приложения

- Один Swift app target, SwiftUI или UIKit для небольшого интерфейса.
- Rust core как статическая библиотека/XCFramework; Swift wrapper держит жизненный цикл handles.
- `BackgroundTasks` для конечного сеанса на поддерживаемых версиях.
- `Network`/системный resolver для наблюдения пути и корректной работы IPv6-only/NAT64.
- Keychain, опционально Secure Enclave для P-256 при доступности; закрытый ключ не экспортируется в логи или backend.
- Associated Domains для открытия из Mini App.
- Никакого VPN extension, локального HTTP listener и доступа к контактам, SMS или Safari cookies.

Для фонового использования ключа предлагается `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; после перезагрузки потребуется первое разблокирование, ключ не переносится на другое устройство через backup. Не требовать биометрию для каждой heartbeat-подписи; пользовательское подтверждение выполняется перед сеансом. [Apple: доступность Keychain](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly).

### 2.4 Настройка проекта

1. Зарегистрировать уникальный bundle ID, например `com.company.leadscout.connect` — заменить на фактический домен/организацию.
2. Добавить Associated Domains `applinks:connect.<product-domain>`.
3. Разместить без редиректа `/.well-known/apple-app-site-association` с Team ID и bundle ID; разрешить только `/connect/*` и `/session/*`.
4. Настроить ключи BackgroundTasks и разрешённые task identifiers по актуальному SDK, с уникальным identifier на batch в допустимом namespace. Не копировать настройки обычного BGProcessingTask вслепую в continued processing task.
5. Проверить регистрацию launch handler до submit, доступность API через `if #available(iOS 26.0, *)` и фактические возможности устройства.
6. ATS оставить включённым. Все управляющие endpoints HTTPS/WSS с действительными сертификатами.
7. Адаптеры Keychain/signature и callbacks не должны блокировать main actor. Обновления UI возвращать на main actor.
8. Для распространения нужны подпись, provisioning, App Store Connect metadata и описание реального поведения сетевого помощника.

Связь домена с приложением задаётся с обеих сторон; установка entitlement без файла на домене недостаточна. [Apple: Associated Domains](https://developer.apple.com/documentation/Xcode/supporting-associated-domains).

### 2.5 Запуск конечного сеанса

Предлагаемый flow:

1. В Mini App пользователь выбирает «Запустить через iPhone».
2. Backend создаёт `batch_intent` с account, пределами действий, сроком и route revision. URL содержит случайный одноразовый intent ID, но не lease/proxy secret.
3. Mini App открывает HTTPS Universal Link. При неудаче остаётся веб-страница с кодом и инструкцией открыть Connect вручную; deep link не считается гарантированным для всех клиентов Telegram.
4. Агент авторизуется собственным device key, читает intent, проверяет owner/device, показывает аккаунт, длительность и разрешённую сеть.
5. Пользователь нажимает «Начать». Только это foreground-действие запускает регистрацию/submit задачи.
6. Использовать submission strategy `.fail` для пилота: если ОС не может начать, вернуть понятное сообщение. Не оставлять неожиданное выполнение в неопределённой очереди.
7. В фактическом launch handler создать cancellation token, установить expiration handler и подключить core. После handshake агент сообщает `BATCH_READY` через STATUS с batch ID.
8. Backend резервирует/подтверждает браузерный слот и активирует lease только для этой партии. Если слот недоступен в стартовое окно, сеанс завершается с «Сервер занят», без долгого фонового ожидания.
9. Пользователь может вернуться в Telegram; действия происходят только пока задача и маршрут живы.
10. По конечному результату backend передаёт BATCH_DONE; агент закрывает все streams и корректно завершает task.

Предлагаемый пилотный предел — до 15 минут или 5 проверенных действий, что наступит раньше. Это внутреннее ограничение продукта, а не установленный Apple лимит. Длинные операции могут не уложиться; следующая партия запускается пользователем заново. Нельзя обнулять срок переименованием batch в фоне.

### 2.6 Реальный прогресс

Сервер заранее определяет конечную работу: например, обработать 5 отобранных вакансий. Он сообщает подтверждённые шаги «проверено», «подготовлено», «отправлено/пропущено/нужна анкета». Общее число шагов согласуется при старте; progress не изображает успех до подтверждения hh.ru.

Агент имеет две метрики: бизнес-прогресс от backend и реальные bytes переданных данных. Heartbeats и таймер не считаются выполненными задачами. Если система считает задачу зависшей или завершает её, backend останавливается по потере маршрута. Apple отдельно описывает прогресс и приоритет прекращения задач с минимальным прогрессом. [Apple: отчётность progress](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/).

ИИ-подготовку по уже имеющимся данным желательно выполнить до запуска телефонного сеанса. Поиск по hh.ru, если он требует устройство, входит в конечный план и его бюджет. Нельзя для удобства заранее обращаться к hh.ru напрямую с IP сервера в режиме DEVICE_REQUIRED.

### 2.7 Остановка и сложные случаи

| Событие | Действие |
|---|---|
| Expiration handler / пользователь отменил task | Локально отменить OPEN и TCP, best-effort STATUS, завершить task неуспешно |
| Force quit | Не рассчитывать на callback; relay обнаруживает закрытие/таймаут, backend помечает спорные изменения |
| Смена Wi-Fi/LTE | Закрыть streams, новая generation, перепроверка; batch не продлевается |
| Нет разрешения на cellular | PAUSED_NETWORK_POLICY, не выбирать сотовую сеть автоматически |
| Телефон перезагрузился | Не восстанавливать batch без нового foreground-действия |
| Капча/OTP требует человека | Показать в Telegram; при длительном ожидании закончить batch и сохранить состояние для нового запуска |
| Проверка/редактирование анкеты | Черновик доступен; отправка требует живой маршрут и отдельного подтверждения revision |
| iOS <26 | Foreground-сеанс; возвращение в Telegram прерывает гарантию выполнения |

На старых iOS одновременный интерактивный login/капча в Telegram и foreground-only агент на том же телефоне может быть неудобен или неработоспособен без второго устройства. Это известный функциональный разрыв, не решаемый обещанием «быстро переключаться». Для такого пользователя предлагается собственный desktop/Android выход либо ограниченный режим без фоновых операций.

### 2.8 Эксперимент, определяющий возможность выпуска

Сначала endpoint под нашим контролем, затем согласованные тестовые действия hh.ru. На реальном iPhone проверить:

- 15-минутный finite batch после возвращения в Telegram;
- блокировку экрана, low power, зарядку, Wi-Fi/cellular/NAT64;
- интервалы без трафика между действиями и серверную ИИ-паузу;
- cancellation, force quit, expiration, нехватку ресурсов;
- исчезновение ложного READY после остановки;
- отсутствие незапрошенного повторного batch после восстановления;
- работу Universal Link именно из поддерживаемых версий Telegram.

Записать модель, версию iOS/SDK, результаты и elapsed time. Если ОС не даёт устойчиво завершать целевой сценарий, релиз ограничивается foreground/device fallback; архитектура не считается доказанной для iOS background.

TestFlight нужен для пилота, App Store — для массового распространения. Модерация оценивает назначение и фоновое поведение; техническая успешность не означает автоматического допуска. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).

## 3. Android

### 3.1 Режим v1

Kotlin-приложение + foreground service на время запрошенного пользователем сеанса. Постоянное уведомление показывает, что устройство передаёт данные LeadScout, объём и кнопку «Остановить». Mini App остаётся основным интерфейсом.

Foreground service не гарантирует вечное исполнение. Тип `dataSync` для приложений, ориентированных на Android 15+, ограничен суммарным временем фонового исполнения; документация описывает 6 часов за 24 часа и callback `onTimeout`. Не планировать бессрочный proxy как бесконечную dataSync-службу. [Android: таймауты FGS](https://developer.android.com/develop/background-work/services/fgs/timeout).

При возвращении пользователем приложения на передний план этот бюджет сбрасывается по правилам ОС. Это не повод искусственно выводить Activity поверх Telegram: новый сеанс начинается явным действием пользователя. Одна остановленная служба и другая служба того же типа не получают независимые шестичасовые бюджеты.

### 3.2 Выбор типа службы — релизное решение

| Вариант | Применение |
|---|---|
| `dataSync` | Пилот конечной пользовательской передачи; подтвердить соответствие фактическому назначению |
| `specialUse` | Кандидат для явно видимого пользовательского сетевого помощника, если стандартные типы не подходят; нужен subtype и проверка магазина |
| `connectedDevice` | Не выбирать только потому, что есть удалённый сервер; соответствие этому типу отдельно обосновывается |
| `remoteMessaging`, `mediaPlayback`, `location` | Не соответствуют назначению приложения и не используются |

`specialUse` требует описания subtype в manifest, которое рассматривается при публикации. Это не автоматическое освобождение от всех ограничений Android/OEM. [Android: типы foreground service](https://developer.android.com/develop/background-work/services/fgs/service-types).

До проверки назначения выпускать короткие пользовательские сеансы, не обещать «автоматически после каждой перезагрузки и 24/7». Подмена типа службы ради обхода временных ограничений не является частью проекта.

### 3.3 Минимальный manifest пилота

Фрагмент для bounded dataSync-варианта; окончательный manifest зависит от подтверждённого типа службы и target SDK:

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

<application android:usesCleartextTraffic="false">
    <service
        android:name=".connect.ConnectService"
        android:exported="false"
        android:foregroundServiceType="dataSync" />
</application>
```

Не запрашивать SMS, accessibility, contacts, root или VPN. Для MVP не добавлять бесконечный wake lock. Если тест выявит реальную необходимость короткого partial wake lock, оформить ограниченный scope/timeout и измерить battery; Doze он сам по себе не отменяет.

Для Android 14+ декларации типа и соответствующего разрешения обязательны при использовании FGS. [Android: требования к типам](https://developer.android.com/about/versions/14/changes/fgs-types-required).

### 3.4 Начало сеанса

1. Mini App создаёт batch intent и открывает verified App Link.
2. Activity авторизует устройство, получает описание сеанса и запрашивает пользовательское действие «Начать».
3. Запускает foreground service из видимого Activity. Служба сразу публикует notification в предусмотренный ОС срок, до длительной сетевой подготовки.
4. Core получает device key callback, policy, quota, batch ID. Открывает control WS и сообщает готовность.
5. Пользователь возвращается в Telegram.
6. Stop action вызывает локальную отмену немедленно, затем сообщает серверу; на сервере отмена не ждёт окончания всего batch.

Общий срок пилотного сеанса — 30 минут, либо меньший пользовательский deadline. Это продуктовая настройка. Foreground service стартует только разрешённым способом; высокоприоритетный push не используется как общий обход ограничений запуска. [Android: ограничения запуска из фона](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

### 3.5 Сеть и батарея

- `ConnectivityManager` сообщает об изменении сети; использовать network generation.
- При Wi-Fi-only остановить/не открыть соединения на metered/cellular пути. Предлагать отдельный лимит мобильных данных; Wi-Fi также может быть metered.
- Существующий VPN пользователя учитывается: не обходить его без явно выбранной политики. Публичный адрес может оказаться адресом VPN.
- DNS resolution и socket dial должны быть связаны с одним выбранным `Network`. Если делегирование в Rust обходит эту привязку, socket создаёт Kotlin adapter и передаёт handle core.
- Captive portal не означает READY: DNS/TCP к нашему relay и проба HTTPS должны пройти.
- `onTimeout` прекращает работу, вызывает stopSelf, сообщает причину. Истёкший сеанс не перезапускается бесконечно.
- `START_NOT_STICKY` для первого релиза: после убийства процесса требуется понятное восстановление пользователем, без обхода его остановки.
- WorkManager можно использовать для ограниченных служебных задач, но не как держатель постоянного reverse TCP-соединения.
- Не требовать отключить энергосбережение у всех. При обнаруженной проблеме дать конкретную диагностику модели и предложить desktop-выход.

### 3.6 Ключи и App Links

P-256 private key создаётся в Android Keystore; аппаратное хранение используется где доступно. Для фонового сеанса ключ не должен требовать нового биометрического подтверждения на каждую подпись. Reinstall/потеря ключа → новая привязка. [Android Keystore](https://developer.android.com/privacy-and-security/keystore).

HTTPS App Links: `android:autoVerify="true"`, точный host/path, `/.well-known/assetlinks.json` с package name и SHA-256 release signing certificate. При Play App Signing используется сертификат подписи устанавливаемого приложения, не произвольный upload key. [Проверка App Links](https://developer.android.com/training/app-links/verify-applinks).

Тестовая команда разработчика после установки сборки:

```sh
adb shell pm verify-app-links --re-verify com.company.leadscout.connect
```

Package name — пример. Кнопка «ввести код вручную» обязательна, поскольку Telegram/пользовательские настройки могут оставить ссылку в браузере.

### 3.7 Распространение

Подписанный APK пригоден для контролируемого пилота. Пользователь получает установщик только с официального HTTPS-домена и видит точное назначение приложения. Массовый канал — Google Play, если правила/тип службы допускают этот сценарий.

Google Play отдельно ограничивает приложения с proxy-функциональностью для третьих лиц: она должна быть их основным видимым назначением; также учитывается использование внешних сервисов. Поэтому выделенный Connect с прозрачным назначением предпочтительнее скрытого сетевого SDK, но не гарантирует одобрение. [Google Play: Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16313518?hl=en-GB).

APK вне магазина не снимает ограничения ОС. Обновление не должно менять подписанта; утрата signing key ломает нормальный путь обновлений. Ключи релиза хранятся отдельно от CI runtime и relay.

### 3.8 Аппаратные проверки

Pixel и хотя бы две распространённые OEM-линейки; Android 14, 15 и актуальная целевая версия. Проверить экран off, Doze, battery saver, ограниченный режим приложения, user stop через системный UI, reboot, Wi-Fi↔LTE, VPN, отказ notifications permission, исчерпание dataSync quota. Ни один из этих случаев не должен переключать hh.ru на серверный IP.

## 4. Windows

### 4.1 Предлагаемый первый релиз

Windows 11 x64, обычное пользовательское tray-приложение. Для оболочки допустим C#/.NET с небольшим native tray UI; core подключается по C ABI. Инсталляция не требует Windows Service, драйвера, admin-прав или изменения системного прокси.

Пользователь после настройки работает в Mini App на телефоне или desktop Telegram. Агент держит исходящее соединение пока активна его Windows-сессия и сеть. Блокировка экрана сама по себе не является выходом из сессии; сон/hibernate и sign out могут разорвать соединение.

### 4.2 Установка и автозапуск

1. Сборка подписанного MSIX с per-user installation и manifest startup task. На первый запуск — явный onboarding.
2. В tray есть «Запускать при входе в Windows». Уважать отключение в Task Manager/Settings, не включать обратно автоматически.
3. Single-instance mutex в пользовательском scope; повторный запуск/ссылка активирует существующее окно.
4. Browser/HH cookies на PC не нужны: используются серверные контексты.
5. Входящих firewall rules не создавать: агент только устанавливает исходящие TCP/443 и соединения к разрешённым destination:443.

Windows StartupTask запускается при входе пользователя; если пользователь отключил его через системные настройки, приложение не может просто включить его программно обратно. [Microsoft: startup tasks](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/desktop-to-uwp-extensions).

Если MSIX недоступен целевой аудитории, альтернативный подписанный per-user installer — отдельный канал с собственными тестами update/uninstall. Не выпускать одновременно два разных автозапуска, создающих два агента.

### 4.3 Хранение и файлы

```text
%LOCALAPPDATA%\LeadScoutConnect\
  config.json       настройки без секретов
  identity.bin      зашифрованный private key, если нет native key handle
  state.json        device ID, последняя версия policy, незавершённый batch ID
  logs\            ротируемые очищенные технические логи
```

Закрытый ключ защищать user-scoped DPAPI и ACL текущего пользователя; не использовать `CRYPTPROTECT_LOCAL_MACHINE`, который расширяет доступ к данным на компьютер. Более сильный native CNG key storage возможен следующим этапом. Кража активной пользовательской сессии всё равно остаётся за границей этой защиты. [Microsoft: CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

### 4.4 Жизненный цикл

- После логина и первого запуска: authenticate → policy → control WS → diagnostic probe → READY.
- Sleep notification: best-effort DRAIN и локальное закрытие sockets. Нельзя полагаться, что уведомление всегда успеет прийти; heartbeat — резерв.
- Resume: новый control handshake/epoch, повторная проверка сети, не оживлять старые TCP streams.
- Exit tray: отмена core, отзыв живых leases на relay, завершение процесса. Закрытие окна настроек может оставить tray, но это должно быть явно понятно.
- Update: DRAIN, подождать безопасную границу с deadline, обновить подписанный пакет, новый handshake; не возобновлять спорную отправку.
- Не отключать sleep глобально по умолчанию. Опция «не засыпать во время активной задачи» — явная, ограниченная временем и реализованная системным power request, если нужна после тестов.

Windows Service для работы до логина — отдельная функция, требующая привилегированного installer, отдельного key store и ACL. Для аудитории 100 человек это добавляет поддержку, поэтому в v1 не входит.

### 4.5 Сети и корпоративные ограничения

Core должен уметь HTTPS CONNECT к корпоративному proxy только для связи с нашим relay, если пользователь явно настроил такой upstream. Target-соединения hh.ru следуют сетевой политике организации; пользовательский VPN/корпоративный шлюз может изменить наблюдаемый IP.

Нельзя выключать TLS verification ради антивируса или TLS inspection. Если официальная политика клиента использует корпоративный root CA, выбор trust store должен быть явно определён и протестирован; иначе дать диагноз, не скрытое insecure-соединение.

Тесты: чистая VM Windows 11, неадминистратор, screen lock, sleep/hibernate, logout, обновление, отключённый startup, user revoke, смена сети, истёкший сертификат, корпоративный proxy, отмена через tray. Отдельно проверить удаление настроек/ключа при unpair и отсутствие процесса после uninstall.

## 5. macOS

### 5.1 Предлагаемый первый релиз

macOS 13+, menu bar app, Swift UI + тот же Rust core. Universal 2 bundle или две проверенные сборки arm64/x86_64. Никаких Network Extension, root daemon, системного VPN или глобальной замены прокси для этой исходящей TCP-схемы не требуется.

Сборка подписывается Developer ID, с hardened runtime, notarization и stapled ticket. Notarization — отдельная проверка безопасности дистрибутива, а не App Store review. [Apple: notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

### 5.2 Установка и привязка

1. Пользователь скачивает signed/notarized DMG, переносит приложение в Applications и запускает.
2. Окно показывает код привязки/QR, доступный для Telegram на телефоне.
3. После двустороннего подтверждения ключ остаётся в Keychain, приложение сворачивается в menu bar.
4. В настройках пользователь включает запуск при входе; использовать `SMAppService.mainApp.register()` и unregister для выключения.
5. UI объясняет, что Mac должен быть включён и не спать. Telegram на Mac запускать не требуется.

Прямой вызов SMAppService из приложения подходит для login item; отдельный helper только ради этого не обязателен. [Apple DTS: SMAppService](https://developer.apple.com/forums/thread/777520).

### 5.3 Разрешения и storage

- Private key в Keychain; синхронизация между устройствами отключена. Secure Enclave опционален, fallback для Intel без подходящей аппаратной поддержки.
- Настройки в `Application Support` без секретов, logs — в каталоге пользователя, с ограничением размера.
- Если выбран sandboxed build: entitlement исходящих сетевых соединений и проверка подписания всех вложенных libraries. Не добавлять listener entitlement без функции, которой он нужен.
- Не требовать Accessibility, Screen Recording, Full Disk Access или браузерные cookies.
- Core и Swift callback работают в фоне, UI на main thread; один экземпляр процесса.
- Keychain access policy подбирается без UI-prompt на каждую фоновую подпись. Если ключ недоступен при lock, показывать PAIRED_OFFLINE до разблокирования; не обещать восстановление control-соединения с недоступным ключом.

### 5.4 Сон, крышка, обновление

Отслеживать sleep/wake события рабочего пространства и состояние сетевого пути. При wake — новый handshake и probe. Не обещать работу с закрытой крышкой ноутбука. Power assertion, если будет добавлен, действует только во время активного задания и по выбору пользователя; не должен трактоваться как гарантированное преодоление lid sleep.

Для первого внешнего пилота допустимо обновление через скачивание нового подписанного DMG. До платного массового релиза нужен проверенный механизм подписанных обновлений с защитой от отката протокола и DRAIN перед заменой процесса. При использовании стороннего updater его версия, подписи и схема key rotation проверяются отдельно; update URL и ключ не берутся из произвольного control-сообщения relay.

Login item выключен пользователем → отображать это в настройках, не создавать скрытый LaunchAgent для обхода. Работать до входа пользователя через LaunchDaemon — отдельный привилегированный продуктовый режим, в v1 отсутствует.

### 5.5 Проверки

Apple Silicon и Intel из заявленной матрицы, свежий пользователь без developer tools, Gatekeeper offline после stapling, deny/disable login item, lock screen, sleep, lid close, Wi-Fi↔Ethernet, VPN, Keychain locked/unavailable, app update, удаление приложения и unpair. Подтвердить отсутствие внешнего browser egress на сервере при каждом обрыве Mac.

## 6. Совместное использование устройств

Один Telegram-пользователь может иметь Mac + Android + iPhone. В Mini App он задаёт выход для каждого своего hh-аккаунта. Default policy — фиксированное устройство, без случайной ротации IP.

Если основной Mac спит, пользователь может запустить телефонный batch и явно сменить маршрут. Backend сначала закрывает старый route revision и спорные операции, потом запускает новый. В v1 маршруты разных владельцев никогда не смешиваются.

Потерянный телефон/проданный ноутбук: revoke в Mini App отзывает устройство; повторная установка требует новой привязки. Удаление приложения без сети само по себе не уведомляет backend, поэтому серверные leases всегда истекают.

## 7. Что требуется от платформенной команды на выходе

Для каждой заявленной платформы передаются:

1. Воспроизводимая release-сборка, подпись и инструкция установки.
2. Работающий pairing, reconnect, stop, revoke и локальные квоты.
3. Аппаратный отчёт lifecycle со списком поддерживаемых режимов и известных ограничений.
4. Проверенный путь обновления, key retention и unpair/uninstall.
5. Единые test vectors протокола и отсутствие расхождений framing между платформами.
6. Реальный замер трафика/батареи/памяти на конечном сценарии.
7. Для мобильных магазинов — фактический статус распространения и соответствие назначению, без подмены его результатом одного сетевого теста.

Наличие исходников, сборка в simulator или успешный foreground ping не закрывают требование работы после сворачивания.
