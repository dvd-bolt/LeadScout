# S-тир LeadScout: пять последовательных модулей

## Как организовать работу

Запускайте пять новых чатов **по очереди** в одной папке проекта. Каждый следующий чат получает
изменения предыдущего. Рекомендуемая модель: `GPT-5.6 Terra`, reasoning `high`.

| Модуль | Одна задача | Результат |
| --- | --- | --- |
| 1 | Диагностика откликов | Видны этап, итог и безопасная причина ошибки каждой попытки |
| 2 | Текст резюме | Текст читаем от источника до интерфейса и ИИ |
| 3 | Мультиаккаунты | Изолированы сессии, данные, задачи, лимиты и остановка |
| 4 | Парсер вакансий | Карточка вакансии разбирается структурно и устойчиво |
| 5 | Цепочка отклика | Сквозные проверки и исправления оставшихся причин сбоев |

В эти пять модулей не входят платежи, редизайн, вход по паролю, ATS/Match Score,
Review First, реферальная программа и ротация AI-ключей. Их стоит делать после стабилизации
текущей автоматизации.

## Передача контекста между чатами

Первый чат создаёт эти короткие рабочие файлы:

```text
docs/s-tier/
  CONTEXT.md
  STATE.md
  reports/
    01-diagnostics.md
    02-resume-text.md
    03-multiaccount.md
    04-vacancies.md
    05-application-flow.md
```

`CONTEXT.md` содержит не более 100 строк: назначение проекта, краткую архитектуру,
пять модулей, команды Windows, правила чтения и проверки. `STATE.md` содержит не более
80 строк: статус каждого модуля (`PENDING`, `IN_PROGRESS`, `VERIFIED_LOCAL`, `BLOCKED`),
окружение, общие контракты, известные проблемы и следующий шаг.

Каждый отчёт в `reports/` ограничен 60 строками: причина, изменения, затронутые файлы,
команды и результаты, контрактные изменения и ограничения. Полные логи остаются отдельно.

Правила для каждого нового чата:

- сначала прочитать `CONTEXT.md`, `STATE.md` и только необходимые отчёты предшественников;
- проверить `git status` и не перезаписывать чужие незакоммиченные изменения;
- воспроизвести проблему, исправить её, добавить содержательную регрессию и проверить результат;
- не ослаблять тесты ради зелёного результата;
- использовать временную SQLite-БД и подменённые внешние отправки;
- не запускать рабочую автоматизацию, не обновлять меню бота и не отправлять реальные отклики
  без отдельного разрешения на конкретный сценарий;
- не писать в логи или отчёты секреты, сессии, полные резюме и ответы анкет;
- обновить `STATE.md` и отчёт своего модуля до перехода к следующему чату.

`VERIFIED_LOCAL` означает только подтверждённую локальную проверку. Живую проверку hh.ru,
Gemini и Telegram нужно отмечать отдельным статусом.

## Промпт модуля 1 — диагностика откликов

```text
Реализуй модуль 1/5 S-тира LeadScout: понятную диагностику попыток отклика.

Мы работаем последовательно в одной папке:
1 — диагностика; 2 — текст резюме; 3 — мультиаккаунты;
4 — парсер вакансий; 5 — сквозная надёжность откликов.

Сначала проверь git status и инструкции проекта. Сохрани существующие изменения.
Автоматические commit/push не нужны.

Создай docs/s-tier/CONTEXT.md и STATE.md.
CONTEXT — до 100 строк: назначение, фактическая архитектура, пять модулей,
команды Windows, правила чтения и проверки из этого задания.
STATE — до 80 строк: статусы модулей, окружение, исходные проблемы,
контракты и следующий шаг. Другие модули первоначально PENDING.

Общие правила для всех пяти модулей:
- Читай сначала CONTEXT и STATE, далее только нужный код и отчёты.
- Расширяй существующие механизмы, сохраняй публичную совместимость.
- Воспроизведи дефект, исправь и проверь регрессию.
- Не ослабляй тесты ради зелёного результата.
- Используй временную БД и подменённые внешние отправки.
- Не запускай рабочую автоматизацию, не меняй меню бота и не отправляй реальные отклики.
- Не публикуй секреты, сессии и личные тексты в логах или отчётах.
- По завершении обнови STATE и отчёт до 60 строк: причины, изменения,
  файлы, команды/результаты, контракты, ограничения.
- VERIFIED_LOCAL означает выполненные локальные критерии. Живую проверку отмечай отдельно.
- Не переходи к следующему модулю.

Подготовь окружение без Docker: проверь Python .venv, зависимости requirements-dev.txt,
Chromium Patchright и сборку web через npm.cmd. Установи недостающее по файлам проекта,
сохраняя закреплённые версии. Выполни исходный тестовый прогон и зафиксируй результат.
Непрофильные исходные сбои перечисли отдельно; исправь только препятствия,
без которых невозможно проверять этот модуль.

Основная задача: у каждой попытки отклика должны быть идентификатор для связи записей,
владелец/аккаунт, ID вакансии, текущий этап, итог и безопасная причина.
Различай поиск, загрузку, разбор, подготовку ИИ, заполнение, отправку и подтверждение.
Фиксируй также остановку и пропуск.

Начни с leadscout/jobs/search.py, jobs/questionnaire.py,
integrations/application_forms.py и storage/repositories/applications.py.
Диагностика и application_events уже существуют — сначала изучи их.

Промежуточные этапы записывай структурированно в ротируемый локальный диагностический лог.
В application_events сохраняй итоговые события: добавление этапов не должно завышать
существующую статистику. Для интерфейса используй существующие status/details и покажи
безопасное объяснение ошибки в истории. Новую административную панель не создавай.

Обработай: истёкшую сессию, CAPTCHA, отсутствие выбранного резюме, недоступную вакансию,
ошибку ИИ, таймаут, неподтверждённую отправку. Не выдавай предполагаемую причину
за установленную.

Проверки: успешная попытка, сбой на разных этапах, пропуск, отмена, однократный учёт
успеха, отсутствие секретов, разделение чужих событий. Логирование не должно скрывать
исходную ошибку или повторять отправку.

Запиши результат в docs/s-tier/reports/01-diagnostics.md.
Не ограничивайся анализом: реализуй и проверь модуль.
```

## Промпт модуля 2 — читаемый текст резюме

```text
Реализуй модуль 2/5 S-тира LeadScout: исправь извлечение и отображение текста резюме.
Работай по docs/s-tier/CONTEXT.md и STATE.md.

Сначала проверь состояние модуля 1 и текущий git diff. Отчёт 01 читай только для нужных
контрактов. Если обязательных файлов контекста нет, сообщи об этом, не выдумывай результаты
предыдущего чата.

Жалоба пользователя: «При просмотре текста резюме появляются битые символы и непонятный текст».
Причина пока не установлена.

Проследи цепочку источник → извлечение → SQLite → API → React → ИИ.
Отдельно проверь резюме, синхронизированное с hh.ru, и импортированный PDF.

Точки входа:
- leadscout/integrations/resumes.py;
- leadscout/documents/pdf_reader.py;
- web/src/features/resumes/ResumeManager.tsx.
Далее переходи к связанным хранилищу/API только по необходимости.

Выясни, что повреждается: кодировка, PDF-шрифты, HTML-сущности, скрипты/стили в DOM,
порядок блоков или отображение переносов. Не применяй массовое перекодирование,
удаление всех необычных символов или подстановку текста через ИИ.

Исправь подтверждённые причины. Сохрани кириллицу, смешанный русский и английский текст,
списки и читаемые абзацы. Неподдерживаемый PDF должен давать понятную ошибку; OCR
в модуль не входит. Не перезаписывай хороший сохранённый текст пустым результатом
или содержимым CAPTCHA/страницы входа. Не переписывай исторические снимки анкет и аудитов.
Если старые данные уже повреждены, опиши восстановление через повторное получение источника;
не запускай массовую обработку рабочей БД.

Используй обезличенные воспроизведения. Если исходного проблемного документа нет,
проверь доказуемые дефекты и явно отметь границу проверки.

Проверки: кириллица, английские термины, сущности, переносы, DOM со служебным содержимым,
PDF с текстовым слоем, нечитаемый PDF, проход текста через БД/API/интерфейс без искажения.
Подтверди, что потребитель ИИ получает тот же содержательный текст.

Добавь нужные регрессии, выполни профильные тесты и сборку при изменениях UI.
Обнови STATE и docs/s-tier/reports/02-resume-text.md. Реализуй только этот модуль.
```

## Промпт модуля 3 — мультиаккаунты

```text
Реализуй модуль 3/5 S-тира LeadScout: проверь и исправь изоляцию аккаунтов
и конкурентную работу. Сначала прочитай docs/s-tier/CONTEXT.md и STATE.md.

Цель: действия одного аккаунта или пользователя не затрагивают другой;
для одного аккаунта несовместимые операции не выполняются одновременно.

Начни с существующих тестов test_multiple_owners.py, test_context_isolation.py,
test_tasks_and_browser.py. Исследуй leadscout/runtime/coordinator.py,
core/concurrency.py, integrations/browser_pool.py и связанные операции только по необходимости.

Построй матрицу проверок:
- два пользователя, по два аккаунта у каждого;
- два AppContext с отдельными временными БД и совпадающими числовыми ID;
- одинаковые и разные прокси;
- повторный вход, выбор резюме, поиск, анкета, синхронизация;
- одновременный запуск, ожидание блокировки, остановка и перезапуск.

Докажи изоляцию cookies/storage_state, текстов резюме, истории, дневных лимитов,
событий и уведомлений. Общий browser pool допускается, общий авторизованный контекст — нет.
Проверь также клиентский выбор аккаунта и кеш запросов, если данные могут смешиваться
при переключении.

Проверь запрет чтения и действий с чужими ID, повторного запуска и повторного подтверждения
одной анкеты, а также остановку работающих и ожидающих задач именно целевого аккаунта.
После ошибки или отмены браузерные слоты и блокировки освобождаются. Смена активного аккаунта
в UI не должна переназначать уже запущенную задачу.

Исправляй воспроизведённые дефекты в существующей архитектуре. Сохрани AppContext,
роли ROOT/ADMIN/USER, проверку revision и лимиты. Не вводи Redis, несколько процессов
или новую систему авторизации.

Для гонок используй управляемую синхронизацию тестов, а не случайные задержки.
Внешние сервисы подменяй; БД, координатор и блокировки проверяй настоящие.
Прогони связанные тесты доступа и lifecycle.

Обнови STATE и docs/s-tier/reports/03-multiaccount.md. В отчёте отдели доказанные
гарантии от сценариев, требующих живых аккаунтов.
```

```text

Прочитай docs/s-tier/CONTEXT.md, STATE.md и краткие отчёты 01–04.

Проанализируй локальные логи адресно, предварительно проверив дату и происхождение.
Старые записи — гипотезы для воспроизведения, а не доказательство ошибки текущего кода.
Не выводи личные данные.

Проверь цепочку:
поиск → загрузка/разбор → выбранное резюме → ИИ → форма → отправка →
подтверждение hh.ru → история/счётчик/уведомление.

Основные точки: leadscout/jobs/search.py, jobs/questionnaire.py,
integrations/application_forms.py и integrations/ai/client.py.

Для каждой воспроизведённой причины неотправки добавь регрессию и исправь первопричину.

при неопределённом результате. Не записывай успех до подтверждения hh.ru.
Не гарантируй exactly-once только уникальным индексом SQLite.

Проверь текущие таймауты и ограниченные повторы Gemini: временные ошибки, 429/5xx,
неверный ключ, некорректный ответ, отмена. Сохрани один настроенный ключ;
ротация ключей и новые провайдеры не входят в этот модуль.

Сквозные локальные тесты должны использовать настоящие сервисы, координатор,
временную SQLite и браузерные формы, подменяя внешние hh.ru/Gemini/Telegram.
Включи обычный отклик, анкету, отказ, дубликат, неизвестный результат, лимит и отмену.
Используй результаты модулей 2–4 в этой цепочке.

Выполни итоговый полный pytest после сборки frontend, Ruff и pip check.
Разбери падения относительно исходного прогона. Не скрывай пропуски браузерных тестов
отсутствующей сборкой.

Подготовь короткий сценарий живой проверки: конкретный аккаунт, резюме, вакансия,
допустимое число отправок и ожидаемые результаты. Проводить внешние действия можно только
при уже имеющемся явном разрешении на конкретный сценарий; иначе закончи всю локальную работу
и перечисли ровно то, что нужно для живого этапа.

Обнови STATE и docs/s-tier/reports/05-application-flow.md: закрытые причины,
доказательства, остаточные ограничения и отдельный статус живой проверки.
Не называй весь S-тир проверенным в production по одним локальным тестам.
```

## Переход между модулями

К следующему чату переходите, когда текущий модуль обновил `STATE.md`, сохранил отчёт
и прошёл свои локальные критерии. Если там стоит `BLOCKED`, сначала устраните препятствие
в том же чате.

После перерыва используйте короткий запрос:

```text
Продолжи модуль N по docs/s-tier/CONTEXT.md и STATE.md.
Проверь текущий diff и отчёт модуля, затем закончи оставшиеся критерии.
```
